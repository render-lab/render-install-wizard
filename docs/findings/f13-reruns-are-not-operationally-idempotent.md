# F13: Re-runs are semantically stable but not operationally idempotent

- Severity: Medium
- Category: Performance
- Status: Confirmed

## Problem

The orchestrator does not call installer `Detect` or `Status` methods before installation, so every run invokes the network installers even when the desired software is already present. Configuration merges also rewrite and rename files when the generated bytes are unchanged. A no-op rerun can consequently download packages, upgrade software, alter file modification times and inodes, trigger agent reloads, or fail because of a new network outage despite requiring no state change.

## Files affected

- `internal/orchestrator/orchestrator.go:185-193`

## Proposed solution

Detect current state before planning each step, distinguish installation from an intentional update, and skip installers when the requested version and scope are already satisfied. Before `atomicWrite`, compare the generated bytes with the existing file and return unchanged without replacing it. Add rerun tests that assert stable mtimes and inodes, zero additional network or package-manager invocations, and success when the network is unavailable after an initial completed installation.
